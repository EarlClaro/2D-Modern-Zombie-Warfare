# Architecture

Status: draft v0.1. Keep minimal; add systems only when a milestone needs them.

## Principles
Ground-plane truth · data-driven `Resource` definitions vs runtime state · explicit signals/APIs, few autoloads · rules separate from UI and from visuals · seedable RNG · measure before optimizing.

## Coordinate spaces (authoritative: [specs/isometric-view.md](specs/isometric-view.md))
- **Ground space**: `Vector2` in *tiles* (float). +X = screen down-right, +Y = screen down-left. All gameplay.
- **Altitude**: separate `float z` (tile-height units). Never folded into ground position.
- **Screen/world-pixel space**: rendering and input only. Conversion only via `IsoProjection`.
- Grid cell = `Vector2i` = `floor(ground)`.

## Module map (created as milestones need them)
```
scripts/iso/       IsoProjection (pure static, no nodes), IsoPicking, SortAnchor
scripts/core/      ContentDefinition (base, id+validate), ContentDb (loads/validates data by id), GameSession (autoload, later), SeededRng helper
scripts/combat/    DamageService (pure), WeaponController, ProjectileSystem, TargetingService, UnitBrain and EnemyIndex (pure, M3), BattleModifiers (pure, M3.5)
scripts/cards/     CardDefinition, DeckDefinition, DeckRules, StateEffectDefinition (Resources); DeckState, CommandPoints, CardPlayService (pure, M2.1); PlacementRules (pure, M2.2), CardTargeting (pure selection + preview state, M2.3)
scripts/missions/  MapDefinition, MissionDefinition, StartUnit, WaveEntry (Resources); MissionRules (pure win/fail, ADR-007), ObjectiveDefinition (data) and ObjectiveTracker (pure, M3.12); later: MissionDirector
scripts/save/      SaveService (autoload, M5)
data/              .tres definitions: cards, units, weapons, enemies, missions
scenes/battle/     Battle.tscn composes: GroundLayer (TileMapLayer), UnitsLayer (y_sort), AirLayer, FxLayer, Camera, HUD
tests/             headless test scripts
```

## Data flow (battle, target M2+)
```
Input (mouse) → IsoPicking → ground pos/cell
  → CardPlayController (checks DeckState + CommandPoints + targeting validity)
      → CardEffects[effect_id].execute(ctx) → DeploymentService / strike scheduler
UnitRuntime nodes → TargetingService → WeaponController → (hitscan | ProjectileSystem)
  → DamageService.apply(attack, target) → Health → died signal
MissionDirector listens to signals (core damaged, enemy died, timer) → evaluates objectives per tick → mission_ended
HUD presenters read state via signals; never mutate rules.
```

## Battle tick (as built, M1.4; cards M2.2)
`BattleController.step(delta)`: (1) clock, **card economy (`DeckState.tick`, `CommandPoints.tick`)**, wave spawns (seeded RNG), (2) enemies choose target/attack or advance and queue damage, (3) player units move/target/fire (hitscan; weapons with `blast_radius` queue falloff damage on every enemy in the ground circle, no friendly fire) and queue damage, then **(3b) `ProjectileSystem.tick`: each shell that lands queues the same kind of blast** (M2.4), (4) apply all queued damage via `DamageService`/`Health`, then remove the dead, (5) `MissionRules.evaluate` (objectives judged on that tick's final numbers). `_physics_process` calls `step` unless `auto_step` is false (tests step manually). Card plays happen between ticks via `play_card(slot, cell)` (validate, spend, discard, lockout, spawn units); the deck has its own seeded RNG so playing cards never shifts spawn jitter. Presentation reacts to signals (`shot_fired`, `blast_landed`, `card_played`, `enemy_died`, `battle_ended`, ...) and never feeds back into rules.

## Flow field (as built, M3.11 part 1)
`FlowField` (`scripts/combat/flow_field.gd`, pure) is the shared distance map of ADR-012: `build(width, height, open, goal)` floods outward from the goal over open cells (a binary heap, 8 neighbours, a diagonal step needs both side cells open); `reachable`, `distance`, `direction_at(p)` (bilinear blend of the four nearest cell headings, each heading the mean of the cell's shortest-path parents), `slide(p, delta)` (moves but never into a closed cell, sliding along it), `trace(from, step)` and `open_grid(map, blocked)`. Ground-plane cells only; no projection maths. 

**Routing (as built, M3.11 part 2).** `MissionDefinition.routing` is `WAYPOINTS` (default: straight segments through `path_cells`, which must not cross scenery) or `FLOW`. For a flow mission `BattleController.setup` builds one field from `FlowField.open_grid(map, db.scenery_cells(map))` toward `core_cell` (terrain and scenery block; units, structures and the core do not, spec D2), and each spawn's `Route` is the field's trace from the spawn. `BattleEnemy.advance(delta, tick)` dispatches: waypoint walkers keep `advance_path`; flow walkers (`_flow` set at `setup`) look up their heading every `STEER_EVERY` (4th) tick, staggered by uid, at `ground_pos + lane` (the lane is the fixed per-enemy offset that spreads a column; it is dropped when that point is on a closed cell), move with `FlowField.slide` (never into a closed cell), and when a step is blocked re-aim with the heading of the cell they stand in. `ContentDb` rejects a flow mission whose spawn cannot reach the core. 

**Separation (as built, M3.11 part 3).** `Separation` (`scripts/combat/separation.gd`, pure) keeps a 1-tile spatial hash of a snapshot of enemy positions and radii (`rebuild`) and answers `push(index, position, radius)`: the sum of unit vectors away from the first `MAX_NEIGHBOURS` (8) other bodies in the 3x3 cells around the position that overlap it, weighted by overlap depth and clamped to `MAX_PUSH`. `MissionDefinition.separation` (default true, flow missions only) makes the controller keep one: it rebuilds the snapshot every `STEER_EVERY` ticks at the start of the enemy phase (each enemy's `sep_index` is its slot) and each walking enemy refreshes `push` (scaled by its speed x `STRENGTH`) every `STEER_EVERY` ticks on the uid stagger, so the cost per tick is level. Attacking enemies stand still and are not pushed; player units and structures are not part of it (spec D6).

**Objectives (as built, M3.12).** `MissionDefinition.objectives` is a list of `ObjectiveDefinition` (kind `SURVIVE` / `CORE_HEALTH_AT_LEAST` / `KILL_COUNT` / `CLEAR_WAVES`, role `PRIMARY` / `SECONDARY` / `FAIL`); empty means the implicit `hold` objective (primary `SURVIVE duration_s`), which is the Milestone 1 rule. `MissionRules` owns an `ObjectiveTracker`; `BattleController.step` fills one reused `ObjectiveTracker.Facts` (core health and maximum, kills, enemies alive, enemies spawned, enemies planned at the chosen difficulty) after damage and deaths and calls `evaluate(core_hp, elapsed, facts)`. Order inside `evaluate` (ADR-007): the tracker updates every objective; then loss is decided first (core destroyed, else a `FAIL` objective or a primary that failed), then win (every primary satisfied and at least one of them completable), so a loss on the same tick as a win stands. A standing objective (`CORE_HEALTH_AT_LEAST`) is pending while it holds and failed for good once broken, so a primary threshold that breaks loses the mission (it can no longer be won) and a secondary one only reports. When the mission ends the tracker settles what is left (standing and held = met, anything else not reached = failed) *before* `ended` is emitted, so the result panel reads final states; `Result.deciding_id` is the objective that decided it (`core` for a destroyed core). The HUD list and the result breakdown read it (3.13, below).

**Objective UI and spawn cues (as built, M3.13).** `ObjectiveText` (pure) turns an `ObjectiveTracker` into `Row`s (text, mark, state, role, deciding) ordered primary, bonus, lose-if; `ObjectiveList` (HUD, a `CanvasLayer`) and `ResultPanel.show_objectives` only draw them, and the list shows only for a mission whose `objectives` is not empty (the HOLD clock of `BattleHud` hides then). `SpawnCue.cue(mission, spawn_index, elapsed)` (pure) says NONE / SOON (with seconds to go, lead 6 s) / ACTIVE (from the wave's start to 2 s after its last enemy); `EdgeArrow.place(point, view, margin)` (pure 2D) puts an arrow on the screen edge towards an off-screen point. `SpawnCueOverlay` (a `CanvasLayer` under the HUD) maps each spawn's ground cell through `IsoProjection` and the camera transform, draws the ring (`IsoProjection.ground_circle_polygon`) when it is on screen and the arrow when it is not. `BattleController._ready` creates both next to `BattleHud`; none of them changes any rule.

## Difficulty (as built, M3.9)
`DifficultyDefinition` (`data/difficulties/`, `ContentDb.difficulties`, `difficulty_ids()` in menu order) holds one number, `enemy_count_mult` (easy 0.6, normal 1.0, hard 1.2), and two pure functions: `scaled_count(n)` = `max(1, round(n * mult))` for any entry that sends enemies, and `scaled_interval(n, gap)`, which keeps an entry's first and last enemy times (a harder wave is denser, not longer, so it still ends inside the mission; an entry whose count did not change keeps its interval exactly). `ContentDb` requires a `normal` that multiplies by exactly 1 and checks a mission's `difficulty_id`.

**Cap (3.10):** `DifficultyDefinition.max_total_enemies` (hard: 2000, 0 = none) limits a level that makes things bigger: `effective_mult(base_total)` = `min(mult, max(1, cap / base_total))`, so a mission that already sends more than the cap at normal is the same on hard, and no level is ever easier than normal. `scaled_count` and `scaled_interval` take the mission's base total (default 0 = uncapped); `MissionDefinition.total_enemies_at` and the controller pass `total_enemies()`. Rounding each entry can leave the total a few enemies above the cap.

`BattleController` resolves the level once in `setup`: the one chosen for the battle (`difficulty_id`: the `--difficulty=` option, or mission select through `GameSession.pending_difficulty`), else the mission's own `difficulty_id`, else normal (an unknown id falls back to normal). It then caches `_wave_count[i]` and `_wave_gap[i]`, which `_spawn_due_enemies` uses instead of the wave's own numbers; nothing else reads the level, so economy, core health, enemy stats, the deck and the cards cannot change with it. A command-line level beats the menu's, and either beats the mission default (a mission default therefore only matters for launches that do not go through the menu). Mission select shows three toggle buttons (also Left / Right), remembers the level in `GameSettings.difficulty` and shows the enemy count at the chosen level; the battle HUD names the level unless it is normal. `GameSession.prepare_battle` (the testable part of `start_battle`) hands the level over.

## Combat drones (as built, M3.7)
`CardKind.SUPPORT_TECH` is an instant card (no cell) that launches autonomous aircraft. The example, Combat Drones, names the unit `combat_drone` (low-air, `behavior = HUNT`, `lifetime_s = 20`, no habits) and a count of 3; they leave the core on a ring (`DRONE_RING`) and are run by the unit brain, not by a sortie plan. `UnitBrain.hunt(pos, anchor, weapon_range, in_range, has_prey, prey)` (pure): stay while something is in range, else fly to the firing spot at 90 % of the range from the prey (the nearest enemy anywhere, `HUNT_SEARCH_RADIUS`), else fly back to the launch spot. Aircraft ignore the walk check (`_carry_out`), so drones cross rock and water. `UnitDefinition.flies_a_plan()` separates sortie aircraft (the helicopter, moved by `_sortie_phase`) from brain-run aircraft. Ground enemies already could not target aircraft, so drones cannot be hurt.

`UnitDefinition.lifetime_s` is general: any unit with one leaves the battle when its time is up (`_expire_phase`, `_retire_unit`), which is not a death and not a loss; 0 keeps the unit until it is destroyed. `ContentDb` requires a SUPPORT_TECH card's unit to be an aircraft that hunts and has a lifetime; `UnitDefinition` allows `HUNT` only on armed, mobile aircraft. A second drone card (more drones, other lifetime or gun) is only `.tres` files, which a test proves.

## Entity cards (as built, M3.6)
Four cards put things on the battlefield. **Minefield** (`CardKind.TRAP`) and **Noise Lure** (`INTEL`) are aimed at an exact cell and name a `FieldEntityDefinition` (`data/entities/`, `ContentDb.entities`): a mine patch (count, spread, trigger radius, damage, blast) or a lure (radius, duration). **Convoy** (`REINFORCEMENT`) is instant and names a unit and a count like a deployment. **Barracks** is an ordinary `DEPLOYMENT` of a structure unit that carries three new `UnitDefinition` fields (`spawns_unit_id`, `spawn_interval_s`, `spawn_cap`); the spec's separate BUILDING kind was not needed.

Pure pieces (all in `scripts/combat/`, no nodes, no randomness): `MineField` (mines laid in a deterministic sunflower pattern; `detonate(enemy_near)` removes and returns the mines that go off), `LureField` (`pull_for(pos)` gives the nearest lure whose radius covers a position; `tick` expires them), `SpawnerState` (one unit per interval while fewer than the cap are alive; at the cap the timer rests at zero, so a replacement always takes a full interval) and `ReinforcementPlan` (picks a settling spot on the enemy's side of the core and the nearest map-edge entry from which the straight walk is clear, trying other angles and edge slides; null when nothing works). `PlacementRules.check_field` allows any walkable cell (roads too, since that is where zombies walk) that is not the core, its walls or scenery, and adds the reasons `NOT_WALKABLE` and `NO_ROUTE`.

In `BattleController`: `_mine_phase` runs right after the enemy phase and queues each triggered mine's blast like any other (enemies only, no friendly fire); `_steer_to_lure` runs for an enemy with nothing in reach: it walks to the lure when the straight walk is clear (re-checked every 6 ticks, staggered by uid) and stands near it, and goes back to its path when the lure ends; `_spawner_phase` runs after the unit phase, counts each building's living units by `BattleUnit.maker_uid` and places a new unit on a free spot beside the building facing the core; `_launch_convoy` spawns the squad on the map edge with the settle spot as each unit's anchor, so a Guard simply walks back to its anchor. `FieldEntityView` draws mines and lures on the decal layer. A convoy with no clear route is refused like a bad cell (`NO_ROUTE`). Limits until the flow field (3.11): lured enemies and returning convoys walk straight lines, and an enemy that leaves a lure heads straight for its next waypoint from wherever it stands.

## State cards (as built, M3.5)
Four card kinds act on the battle's state instead of the map: `ORDER` (a timed armour or damage change, e.g. Fortify), `SUPPLY` (Command Points and aircraft missiles, e.g. Supply Drop), `DECK` (draw cards, e.g. Quick Draw) and `DOCTRINE` (a permanent change that a mission starts with, e.g. Hollow Points). Each card names a `StateEffectDefinition` (`data/effects/*.tres`, `ContentDb.effects`) through `effect_id`; the effect holds the numbers (`duration_s`, `armor_bonus`, `damage_mult` + `weapon_ids`, `cp_gain`, `refill_ammo`, `draw_count`), so a new card of these kinds needs only `.tres` files. `ContentDb` checks that the effect exists and fits the kind (an order is timed and changes armour or damage, a doctrine is permanent, a supply card gives CP or reloads, a deck card draws, weapon ids exist, a mission only names doctrine cards) and `DeckRules` refuses a doctrine in a deck.

`BattleModifiers` (pure, keyed by effect id, so playing an order again refreshes its timer and never stacks) holds what is in force: `armor_bonus()` is added to the armour of every player ground unit when an enemy hits it (the core has none), and `damage_mult(weapon_id)` scales the damage of a player weapon at the moment it fires (`BattleController._fire`). The controller ticks it with the battle clock and clears it on restart, then re-applies the doctrines named by `MissionDefinition.doctrines` and `BattleController.extra_doctrines` (the `--doctrine=a,b` launch option, until the pre-mission picker exists in M5). Instant cards (order, supply, deck) take no target: `select_slot` plays them on the click (`play_card` ignores the cell), a refusal is reported through `card_rejected` like any other, and a doctrine card in a hand is `UNAVAILABLE`. The hand bar colours and labels the new kinds and lists the orders and doctrines in force above the CP bar.

## Unit behaviours (as built, M3.3)
Placed units decide for themselves (ADR-013); the player gives no move orders. `UnitBrain` (`scripts/combat/`, pure, no randomness) turns facts supplied by the battle into a `Decision` (stay, or move to a spot): `guard` (anchor + leash: go after the nearest enemy near the anchor, take a firing spot at 90 % of weapon range clamped to the leash, return to the anchor when idle), `advance` (go toward the enemy closest to the core, clamped to `advance_limit` from the core), `support` (stand next to the nearest friendly fighter), and HOLD (nothing). Every behaviour stops the moment something is in weapon range, because units fire only while standing. `UnitDefinition` carries `behavior`, `leash`, `advance_limit`, `follow_range` and `effective_behavior()` (fixed units and structures always hold). `BattleController._think_and_move` asks the brain, `_carry_out` validates the walk (`_walk_is_clear`: walkable terrain, not the core cell, not scenery; otherwise the unit stays) and issues the move through `BattleUnit.order_move`, which only the brain and the sortie flights use now. `BattleUnit.anchor` is the cell centre where the unit was placed. Sortie aircraft skip the brain. The enemy phase also records the enemy closest to the core (`_front_pos`) for ADVANCE units. Known limits: units walk straight lines (no routing around obstacles until the flow field, 3.11), do not avoid each other, and the Support behaviour only follows (healing and repair arrive with the support cards in 3.5).

### Habits (as built, M3.4)
Three switchable habits sit on top of the behaviours (`UnitDefinition.seeks_cover`, `retreats` + `retreat_below` 0.35, `focus_fire`, all on by default). **Cover:** a GUARD that has an engaged enemy and is not yet in cover walks to `UnitBrain.cover_spot` (just behind the friendly structure, seen from the enemy, in weapon range, inside the leash, at most 6 tiles of walking) even if it could already fire, unless an enemy is within 3 tiles; once within 1.5 tiles of a structure that is nearer the enemy it counts as `in_cover` and stays, so a creeping enemy does not make it shuffle. The benefit is not a damage bonus (there is none): enemies attack the nearest thing, so the structure takes the blows. **Retreat:** a mobile unit whose health fraction is below `retreat_below` walks to 2.5 tiles from the core while any enemy is within 7 tiles, and stays put otherwise; fixed units never retreat; there is no healing yet (3.5), so a retreated unit stays hurt. **Focus fire:** `EnemyIndex.best_in_range` picks the highest score among enemies in weapon range, then the nearest, then the lowest uid; score = `EnemyDefinition.threat` (spitter 2, brute 1, others 0) + 3 for an armoured enemy when the weapon is `anti_armor` (RPG, tank cannon); with no threats it equals `nearest`. Enemies keep nearest-wins.

## Enemy index and target queries (as built, M3.2)
`EnemyIndex` (`scripts/combat/`, pure apart from holding `BattleEnemy` references) is a 2-tile uniform grid over the map built with linked lists in packed arrays. `_enemy_phase` clears it, moves each enemy, then adds it at its new position; `_unit_phase` and `_queue_blast` query it (`nearest(origin, range)`, `box_candidates(centre, radius)`), and `_index_ready()` rebuilds it from `enemies` if it was marked stale (spawn, removal, restart). Answers equal a full scan: smallest squared ground distance, exact ties to the lowest id, blast candidates in `enemies` order with the caller applying the exact falloff. The enemy phase itself no longer builds target objects: it keeps the ground units' positions in reused packed arrays and rejects enemies that are too far from every target before comparing distances (same nearest-wins, lowest-id-on-ties rule as `TargetingService.pick`, which stays as the reference the tests compare against).

## Projectiles and operations (as built, M2.4)
`ProjectileSystem` (`scripts/combat/`, pure) keeps shells as parallel packed arrays, not nodes: a straight ground line `from`->`to`, altitude as a parabola on top (`altitude_profile`), a negative age = launch delay, cap 256, lands exactly once (1e-6 tolerance so a 0.9 s flight lands on its 54th 1/60 s tick). Ground position never depends on altitude. Measured: 256 shells in flight cost 0.46 ms per tick incl. per-shell queries. `OperationDefinition` (`data/operations/`, referenced by `CardDefinition.effect_id`) holds the barrage parameters and the even-spread (Vogel spiral) scatter + shuffled firing order from a dedicated seeded RNG. `BattleController` turns a played Operation card into queued shells plus a `Strike` telegraph (`strikes`), emits `strike_called` / `blast_landed`; views `StrikeTelegraph` (ground, `Decals` layer) and `ProjectileView` (one node drawing every shell + its ground shadow, new `Air` layer) only read that state. Blasts share one path (`_queue_blast`): armor, then distance falloff, enemies only.

## Sorties and missiles (as built, M2.5)
A Sortie card flies one aircraft along a `SortiePlan` (pure: nearest map edge -> station over the target -> opposite edge, entry/exit 5 tiles off the map) driven by `SortieFlight` (pure state machine ENTERING -> ON_STATION for `station_time_s` -> LEAVING -> DONE; the controller issues the move orders and removes the aircraft at DONE, which is not a loss). `BattleAircraft extends BattleUnit`: its node sits at the lifted screen position (ground position + altitude) on the unsorted `Air` layer, while `ground_pos` stays ground-plane truth and the `IsoShadow` stays on the ground. Ground enemies never target aircraft; aircraft never block build cells or fade the core. Weapons gained `ammo` (0 = unlimited), `can_fire_moving`, and real `PROJECTILE` delivery (`projectile_speed` = average speed, `projectile_accel` rocket-motor acceleration, `projectile_drop` launch dip). A unit may carry a `secondary_weapon_id` with its own cooldown/ammo: the helicopter fires its missile load (alternating wing pylons, firing on the move without turning off its flight line) on the way in, then hovers and uses the machine guns. Missiles are `ProjectileSystem` entries (kind MISSILE, launch altitude descending to the target, eased progress) that land through the same `_queue_blast` as shells. `ProjectileView` draws missiles as finned rockets with a motor flame, a continuous smoke trail and lingering puffs; `Explosion` (ground-radius fireball + shockwave + scorch + smoke) shows every area blast at its true radius.

## Card UI (as built, M2.3)
`CardTargeting` (pure) holds the selected hand slot and builds a `Preview` (valid?, why not, weapon range, blast radius, where units would stand) for the cell under the mouse; `BattleController` exposes `select_slot` / `cancel_selection` / `confirm_at(cell)` and the current `preview`, and emits `card_rejected`. `HandUi` (`ui/hand_ui.gd`) draws the five slots, CP pips, draw timer, pile counts, refusal toast and a cursor tooltip, and sends clicks back through the controller; `CardPreview` draws the target cell, range/blast ground circles and the deploy zone through `IsoProjection`. Both only read state; rules never live in them. Layout maths (`HandUi.slot_rect/slot_at/capture_rect`) is static and tested.

## Presentation (as built, M1.5)
`BattleFeedback` (a child of the battle) is the only presenter: it subscribes to controller signals and spawns transient effects on the controller's Fx layer, plays sounds through `SfxService`, shakes the camera and flashes/kicks entities. Rules never read anything it produces (verified by a test that runs the same battle with and without it). Entities carry only cosmetic helpers (`IsoEntity.flash`, `play_death`, `BattleUnit.kick`). Sound pooling is pure logic (`SfxVoicePool`).

## Progression profile (as built, M5.1)
`scripts/progression/`: `PlayerProfile` is plain data (collection, deck, doctrines, finished missions, reward offers) with `to_dict` / `from_dict` that never fail and `sanitize(db)` that drops unknown ids and repairs an illegal deck; `ProfileStore` reads and writes `user://profile.json` (every function takes a path; temporary file then swap, `.bak` of the last good file, damaged files set aside, newer files read-only); `ProfileMigration` upgrades old files one version step at a time. `GameSession.profile()` holds the shared profile like it holds the settings (no autoload). Battle, combat and card code never read it. Spec: [progression.md](specs/progression.md).
Campaign (M5.2): `CampaignDefinition` (`data/campaigns/main.tres`, loaded by `ContentDb`, ids checked against the missions) holds the unlock order and the unlock rules; `MissionListing` orders and tags the missions from it; `MissionSelect` shows locks and results. `ProgressRecorder` is a node the battle gets only when the menu started it; it listens to `battle_ended` and writes a win into the profile and the file, so the battle's own rules never see the profile.

Rewards (M5.3): `RewardPicker` is pure (pool, owned cards, seed, mission id gives up to three card ids); `ProgressRecorder` opens the offer on a first win and `PlayerProfile` keeps it in `offers` until `GameSession.claim_reward` takes a card from it and saves; `RewardChooser` is the one widget used by the result panel and by mission select. Pools live in `CampaignDefinition.reward_pools`.

Deck editor (M5.4): `DeckBuilder` (pure) holds every editing rule over a `PlayerProfile` and the shipped `DeckRules` and builds the `loadout` a battle receives; `DeckScreen` only presents it and saves through `GameSession`. A mission with `deck_source = PLAYER` gets that loadout through `BattleController.deck_override` and `extra_doctrines`, set by the battle scene only when the menu started it; combat and card code never see the profile.

Upgrades (M5.5): `UpgradeDefinition` holds `UpgradePatch`es (number changes on a weapon, unit, operation or card, validated when the content loads). `UpgradeApplier.patched_db` copies the database tables and duplicates only the definitions a patch changes; the battle scene gives that copy to a menu-started player-deck battle. The profile stores `unlocked_upgrades` and `equipped`; the shared definitions, the tools and fixed-deck missions never see an upgrade.

Balancing player-deck missions (M5.6): `SampleDecks` describes three example players (picks from the real reward pools, deck, upgrades, doctrine) and builds their `PlayerProfile`; the balance tool plays missions with their `DeckBuilder.loadout` and the `UpgradeApplier` copy of the content, the same path the battle scene uses for a real player.

## Key design choices
- **Pure logic classes** (`RefCounted`, no Node dependency) for IsoProjection, DamageService, DeckState, CommandPoints, objective evaluation → trivially headless-testable.
- **Definitions vs runtime**: `CardDefinition` (Resource, immutable) vs `CardRuntime`/`DeckState` entries (id + mutable lockout).
- **Projectiles**: data-oriented `ProjectileSystem` holding arrays of ground pos, velocity, z, vz; one `_physics_process`; rendered via one MultiMesh or `_draw` (decide in M1 by measuring). Not one node per bullet.
- **Physics**: ground-plane footprints (circles). Godot 2D physics used minimally (no physics in screen space). Hit detection = ground distance + altitude range overlap.
- **Layers** (CanvasItem z/y-sort): Ground tiles → shadows → ground entities (y_sort_enabled) → air entities → FX → HUD (CanvasLayer).
- **Hordes**: per-agent steering over a shared flow field is the leading candidate; decision deferred to M3 (A6). **M1 measurement:** straight-line waypoint walking for 100–500 enemies costs 0.5–1.9 ms per tick headless (see BALANCE.md), so path-following is not the bottleneck yet; the open problems are separation/overlap and real obstacle avoidance, which only matter once maps have non-trivial walls (M3+).
- **Autoloads (planned, max 4)**: `GameSession`, `SaveService`, `AudioService`, `SceneRouter`. None before they're needed.

## Testing seam
Anything with rules is a `RefCounted` class taking an injected `RandomNumberGenerator` and config; scene scripts are thin. See [TESTING.md](TESTING.md).
